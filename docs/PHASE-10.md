# Phase 10 — Documents and Dashboard

## Exit criterion

> An uploaded file can never be executed, never escape its directory, and never
> be read by someone who cannot read the record it hangs on. The dashboard
> leaks no count to anyone who lacks the permission for it.

Both met, each with tests that fail if broken.

## What was delivered

**Document upload** — files attached to any of thirteen record types, with
category, title, restriction flag and checksum. List, download, soft delete,
storage summary.

**Dashboard** — a hero figure, a stock bucket breakdown, per-module tiles, a
week of ledger activity, and an attention list of things needing a person.

## Documents: a list of things we refuse

File upload is the richest vulnerability surface in a web application, so every
decision here goes the restrictive way.

**An allowlist, never a blocklist.** Eight accepted MIME types, each with one
canonical extension. A blocklist is a bet that you thought of every dangerous
type, and that bet loses the first time a browser learns to execute something
new.

Three absences are deliberate:

* **SVG** is XML, it can carry `<script>`, and the browser executes it when
rendered inline. An image format that runs code is not an image.
* **HTML** — the same, with less disguise.
* **ZIP** cannot be inspected without unpacking it, and unpacking untrusted
archives is its own vulnerability class (zip bombs, traversal via crafted
entry names).

**The declared type is a hint, not evidence.** `Content-Type` comes from
whoever is uploading. Every file's leading bytes are checked against the type it
claims, so a Windows executable announced as `image/png` is refused — and
refused *before* anything is written, because multer is configured for memory
storage rather than disk. A file that lied about itself never exists on our
filesystem at all.

**Path traversal is unreachable, not validated against.** Two names are kept:
`originalName` is what the uploader called it and is display-only;
`storageKey` is what we called it — 32 random bytes, sharded by tenant, with
the extension taken from the *verified* type. No request data is ever
concatenated into a path. A test reads `storage.js` and fails if a future edit
threads the uploader's filename through.

There is still a `resolveKey` guard that refuses any key escaping the storage
root. Keys are generated by us and should never need it; it costs two lines and
removes a class of outcome.

**A document is exactly as confidential as the record it hangs on.** Every
upload, list and download resolves the parent and checks the permission for
*that* record type. Without it, attaching a file would be a side door: anyone
with `CREATE\_DOCUMENT` could attach to a purchase order they cannot read and
then read it back, and the file list would reveal which records exist. A unit
test asserts every entity type maps to a model that exists and a permission that
exists — which caught a real mistake during this phase, where the transfer entry
pointed at `StockTransfer` and the model is called `WarehouseTransfer`.

**Restricted documents are listed but not downloadable.** Hiding them entirely
would stop an auditor noticing a document was missing from a record. The
filename is not the sensitive part; the contents are. Every denied attempt and
every successful download is written to the audit log, because marking a
document restricted should mean access is both controlled and *accounted for*.

**The download headers do the rest.** `Content-Disposition: attachment` for
anything not provably safe to render — a file rendered inline executes in our
origin, which turns an upload into stored XSS. `X-Content-Type-Options: nosniff` stops the browser second-guessing us. A `sandbox` CSP applies even to
the inline-safe types. The filename is stripped of quotes and control
characters, because an unescaped name is header injection.

**The checksum is verified on the way out.** If the stored bytes no longer hash
to what was recorded, something changed them, and serving a file we can no
longer vouch for is worse than failing.

**Deleting keeps the bytes.** A document attached to a goods receipt is
evidence. A user pressing delete is making a filing decision, not granting
permission to destroy the artefact. Purging is a separate, deliberate operation.

## Dashboard: two rules

**A count is data.** Every panel is gated by its module's permission, and an
unpermitted panel is *absent* rather than zeroed — zero is itself an answer.
Telling a Sales Dispatch user "14 purchase orders awaiting approval" leaks the
existence and volume of purchasing activity to someone with no
`VIEW\_PURCHASE\_ORDER`. The unpermitted panels also cost no query, which is the
other benefit of gating properly rather than filtering afterwards.

**Nothing is stored or cached.** Every number is computed from the same records
the detail screens read, so the dashboard cannot disagree with the page you
reach by clicking it. A nightly job writing dashboard totals would be faster and
would eventually be wrong — and a wrong dashboard is worse than a slow one,
because people stop trusting the whole system.

The route itself requires no permission. A blanket `VIEW\_DASHBOARD` would be a
second, weaker gate that could disagree with the real ones, and the first time
they disagreed, one of them would be leaking.

## The chart decisions

The stock breakdown is **a stacked bar, not a pie**. The job is comparing
magnitudes of parts; a stacked bar compares lengths against a common baseline,
a pie asks you to compare angles, which people cannot do.

The five bucket colours are a categorical palette assigned in fixed slot order
and never cycled — colour follows the entity, so an empty bucket does not
repaint the others. The palette was **run through a validator rather than eyed**:
it passes the lightness band, chroma floor, colour-vision-deficiency separation
(worst adjacent ΔE 9.1 light / 8.4 dark) and the normal-vision floor (19.6 /
19.3). Light mode flags a sub-3:1 contrast warning on three slots, which
obliges relief — so every segment wide enough carries a direct label and the
legend repeats every value as a table. Identity is never colour alone.

Dark-mode steps are recorded in the source but **not applied**: the app is
light-only today. They are kept because a flipped light palette does not survive
a dark surface, and whoever adds dark mode should not have to rediscover that.

Status colours in the attention list always travel with an icon and the severity
in words — two of the four status steps are deliberately sub-3:1 on a light
surface, and the icon is the mitigation.

The Phase 1 permission inspector survives, collapsed. It was the fastest way to
confirm the permission matrix was behaving, and it still is.

## Not in this phase

Printable documents — a PDF warranty certificate, a return note — are generation
rather than storage, and belong with reports in Phase 11. Virus scanning needs a
scanner (ClamAV or a hosted API) and is a deployment decision for Phase 12; the
type and content checks here reduce the surface but are not a substitute.
